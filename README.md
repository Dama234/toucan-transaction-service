# Transaction Management Service

A small transaction-processing service built with Spring Boot as part of the **Toucan Payments Engineering Challenge 2026**.

---

## 1. Problem Understanding

The service manages customer transactions. Each transaction holds:

- **Transaction ID** — Unique identifier (UUID)
- **Customer ID** — Reference to the customer
- **Amount** — Monetary value
- **Currency** — 3-letter ISO code (e.g. USD, EUR)
- **Transaction Type** — DEBIT, CREDIT, or TRANSFER
- **Transaction Status** — PENDING, COMPLETED, FAILED, or CANCELLED

The service exposes **four operations**:

1. **Create** — Accept and store a new transaction
2. **Get** — Retrieve a transaction by ID
3. **Update status** — Change the status of an existing transaction
4. **List by customer** — Retrieve all transactions for a given customer

---

## 2. Assumptions Made

- **Transaction IDs are auto-generated by the server as UUIDs** by default, but clients may optionally provide their own ID. If a client provides an ID that already exists, the request is rejected with 409 Conflict (per docx Section 4A).
- **All new transactions start in PENDING status** — the system, not the user, decides the initial state.
- **Currency is stored as a 3-character string** matching the ISO 4217 format (e.g. "USD", "EUR", "GBP").
- **Amount is always positive** — negative or zero amounts have no real-world meaning in this context.
- **Status transitions are one-way** — once a transaction reaches a terminal state (COMPLETED, FAILED, CANCELLED), it cannot change further.

---

## 3. Validation Rules

All rules are defined in `TransactionController.CreateTransactionRequest` and enforced by the `@Valid` annotation on the controller method.

| Field | Rule | Why |
|---|---|---|
| `customerId` | Not blank | A transaction must belong to a real customer. |
| `amount` | Greater than zero | Zero or negative amounts make no business sense. |
| `currency` | Exactly 3 characters | Matches the ISO 4217 standard for currency codes. |
| `type` | Must be a valid enum value (DEBIT, CREDIT, TRANSFER) | We need to know the transaction direction. |

**Field-level annotations used:**
- `@NotBlank` — String cannot be null, empty, or whitespace.
- `@Positive` — Number must be > 0.
- `@Size(min = 3, max = 3)` — String length is exactly 3.
- `@NotNull` — Value cannot be null.

**Validation runs automatically** when a request hits the controller. If validation fails, the client gets a 400 response with a list of all problems, not just the first one.

## 4. API Endpoints

All endpoints are under `/api/transactions`.

| Method | Endpoint | Description | Success | Errors |
|---|---|---|---|---|
| `POST` | `/api/transactions` | Create a new transaction | 201 Created | 400, 409 |
| `GET` | `/api/transactions/{id}` | Get transaction by ID | 200 OK | 404 |
| `PUT` | `/api/transactions/{id}/status?status=COMPLETED` | Update transaction status | 200 OK | 404, 409 |
| `GET` | `/api/transactions/customer/{customerId}` | List transactions for a customer | 200 OK | — |

### Example: Create

```http
POST /api/transactions
Content-Type: application/json

{
  "id": "txn-001",        // optional — auto-generated if omitted
  "customerId": "cust-001",
  "amount": 100.50,
  "currency": "USD",
  "type": "DEBIT"
}
```

> If the optional `id` is provided and already exists, the API returns **409 Conflict** (per docx Section 4A "Reject a Transaction ID that already exists").

**Response (201):**
```json
{
  "id": "txn-001",
  "customerId": "cust-001",
  "amount": 100.50,
  "currency": "USD",
  "transactionType": "DEBIT",
  "status": "PENDING"
}
```

### Example: Update Status

```http
PUT /api/transactions/{id}/status?status=COMPLETED
```

The query parameter `status` can be `COMPLETED`, `FAILED`, or `CANCELLED`.

## 5. Status Transitions

```
PENDING ──────► COMPLETED
    │
    └──────► FAILED
    │
    └──────► CANCELLED
```

**Rules:**

1. A new transaction is always created in `PENDING`.
2. From `PENDING`, the status can change to `COMPLETED`, `FAILED`, or `CANCELLED`.
3. `COMPLETED`, `FAILED`, and `CANCELLED` are **terminal** — no further transitions allowed.
4. Attempting a forbidden transition returns **409 Conflict**.

**Reasoning:** In real payment systems, once a transaction is completed or failed, the result is final. Allowing changes afterward would break audit trails and create ambiguity in financial reporting.

---

## 6. Error Handling

| Status Code | When | Body |
|---|---|---|
| **201** | Transaction created | The new transaction JSON |
| **200** | Operation successful | The result JSON |
| **400** | Validation failed | `{ "error": "Validation failed", "details": [...] }` |
| **404** | Transaction not found | Empty body |
| **409** | Invalid status transition OR duplicate transaction ID | Empty body |

The `GlobalExceptionHandler` catches all validation errors and returns a clean, machine-readable error format.

## 7. Project Structure

```
src/
├── main/java/com/example/transactionstarter/
│   ├── TransactionStarterApplication.java   # Main entry point
│   ├── model/
│   │   ├── Transaction.java              # JPA entity
│   │   ├── TransactionType.java         # Enum: DEBIT, CREDIT, TRANSFER
│   │   └── TransactionStatus.java        # Enum: PENDING, COMPLETED, FAILED, CANCELLED
│   ├── repository/
│   │   └── TransactionRepository.java    # Spring Data JPA
│   ├── service/
│   │   └── TransactionService.java       # Business logic
│   ├── controller/
│   │   └── TransactionController.java     # REST endpoints
│   ├── dto/
│   │   └── CreateTransactionRequest.java # Request DTO with validation
│   └── exception/
│       ├── GlobalExceptionHandler.java   # Error responses
│       └── DuplicateTransactionException.java # Duplicate ID exception
└── test/
    └── java/com/example/transactionstarter/
        └── TransactionStarterApplicationTests.java  # 8 integration tests
```

**Why this structure?**
- **Entity** owns the data shape.
- **Repository** owns database access.
- **Service** owns business rules (especially status transitions).
- **Controller** owns HTTP concerns only.

Each layer has one job, which makes the code easier to test and change.

## 8. How to Run

### Prerequisites
- Java 17 or higher
- No other installation needed (Maven wrapper is included)

### Run Tests
```bash
# Linux / macOS
./mvnw clean test

# Windows
.\mvnw.cmd clean test
```

**Expected output:**
```
[INFO] Tests run: 8, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

```bash
# Linux / macOS
./mvnw spring-boot:run

# Windows
.\mvnw.cmd spring-boot:run
```

Use Postman, PowerShell, or curl. Examples:

## 9. Testing Approach

Eight integration tests are included. Each one tests a real behavior, not just that the code compiles.

| Test | What It Checks |
|---|---|
| `createTransaction_shouldReturn201WithId` | Creating a transaction returns 201 and a non-empty ID |
| `getTransaction_shouldReturn200AndTransaction` | Reading a created transaction returns the same data |
| `updateStatus_shouldChangeStatusToCompleted` | Status update persists and is reflected in the response |
| `getTransactionsByCustomer_shouldReturnAllForCustomer` | Filtering by customer returns all matching records |
| `updateStatus_invalidTransition_shouldReturn409` | Forbidding a bad transition returns 409 Conflict |
| `getTransaction_unknownId_shouldReturn404` | Missing resources return 404, not 200 with empty data |
| `createTransaction_invalidData_shouldReturn400` | Validation errors (blank ID, negative amount, wrong currency length) return 400 Bad Request |
| `createTransaction_duplicateId_shouldReturn409` | Duplicate client-provided transaction ID is rejected with 409 Conflict |

**Why integration tests?**
They exercise the full HTTP → Controller → Service → Repository → Database path. This catches problems that unit tests would miss, like JSON parsing issues or JPA mapping errors.

## 10. Known Limitations

1. **No pagination** — `GET /customer/{id}` returns all transactions. For a customer with thousands of transactions, this would be slow. A `Pageable` parameter could fix this.
2. **No filtering** — Cannot filter by status, date range, or amount. A query string parameter would help.
3. **No authentication** — Anyone can create or read any transaction. In production, this would need an auth layer.
4. **In-memory database** — Data is lost on restart. Using PostgreSQL or MySQL would make it persistent.
5. **No API documentation** — OpenAPI / Swagger is not configured. Could be added with the springdoc dependency.

---

## 11. What I Would Improve With More Time

1. **Pagination** on the customer list endpoint using `Pageable`.
2. **Filtering** by status, date range, and amount.
3. **Audit log** — A separate table tracking every status change with timestamp and actor.
4. **Validation on Transaction ID** — If clients can provide IDs in the future, add `@Pattern` or uniqueness check.
5. **OpenAPI documentation** — Add springdoc-openapi for auto-generated Swagger UI.
6. **Exception logging** — Add a logger to `GlobalExceptionHandler` to record errors server-side.
7. **Request size limits** — Prevent oversized JSON payloads.
8. **More tests** — Add edge cases like very large amounts, special characters in customerId, etc.
